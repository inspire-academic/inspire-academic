## Decisions I made without asking, and why (flag any of these if you disagree)

- **Did not touch `assessment-engine/assessment-engine.html` or `assessment-report.html`'s underlying logic.** The brief was explicit — "do not build a second diagnostic engine, do not build a second reporting engine" — and both already do the job (guest-accessible, deterministic, no per-attempt AI cost, already produces a strengths/gaps/plan narrative). I did not even rename the report to "Mastery Snapshot" globally, because that page is shared by every diagnostic user on the platform, not just ISM families — relabelling it site-wide would mislabel it for everyone else. "Mastery Diagnostic" / "Mastery Snapshot" language is confined to the new `programmes/science-mastery/` pages only.
- **Did not wire the diagnostic-completion email into `leads`.** The plan's original intent was to also capture a lead the moment someone emails themselves their diagnostic PDF, closing the loop for a family who diagnoses without registering first. On inspection, `assessment-report-email.js` is a shared, platform-wide function whose payload (`recipientEmail, studentName, subject, level, board, currentGrade, targetGrade, pdfBase64, filename`) has no parent name or phone number — both `NOT NULL` on `leads`. Forcing that shared function to synthesize fake values, or loosening those constraints platform-wide, felt like the wrong trade for a same-day build. **Net effect: registration (`programmes/science-mastery/register/`) is the only point that creates a lead today.** A family who reaches the diagnostic without registering first and only ever emails themselves a report will not appear in the pipeline. If that gap matters in practice, the fix is a small dedicated capture step on the report page itself, not a change to the shared email function.
- **Built a new `ism_pipeline` table instead of extending `leads`.** `leads.status` is a 4-value constraint (`new/contacted/enrolled/lost`) shared by every other programme's landing page — redefining it to the 12-value ISM vocabulary would have been a destructive, cross-programme schema change for no real benefit, especially since `leads.html` (the existing admin view) has no update capability at all today. `ism_pipeline` links back to its source `leads` row via `lead_id` so nothing is duplicated by accident — a lead only becomes a pipeline record when a member of staff deliberately adds it (or converts a fresh registration) from `programmes/admin/ism-pipeline.html`.
- **No Gmail/email automation was built**, per the brief's explicit instruction. Every template in the launch pack (`03_PARENT_OUTREACH/Parent_Launch_Letter.md`, etc.) is copy for you to paste and send by hand or via mailto — nothing in this build sends anything automatically. The one exception is the *existing* Resend-based diagnostic-report email, which was already live before this campaign and only fires when a user explicitly requests their own report.
- **CSV import maps the full pipeline sheet, not just names/contact details.** Since you'll likely fill in `ISM_100_Family_Pipeline.csv` progressively (status, review dates, offers, notes) rather than all at once, the importer on `programmes/admin/ism-pipeline.html` reads Status, Review Date, Offer (mapped to tier), Paid?, and Notes (logged as a communication-log entry) as well as the contact fields — so re-importing an updated sheet is a realistic workflow, not a one-time bulk-add.
